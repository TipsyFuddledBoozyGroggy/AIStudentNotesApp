# Cross-review of Opus's half of ADR-022 (senior-engineer-fable)

Date: 2026-11-27. Step 4 of the pairing protocol. Reviewed: the working tree as it stood this afternoon (`git diff` plus the untracked files in Opus's ownership list): `docs/API_CONTRACTS_AUTH.md`, the Identity module (`Google/`, `KeyRing/`, `IdentityModule.cs`, `IdentityEndpoints.cs`, `SessionPolicy.cs`, the DbContext and migration `M010_GoogleSignIn`), `Program.cs`, `RootSecret.cs`, the new integration tests and the web sign-in files. I read the code; I did **not** run Opus's test suites. I did run the API built from this tree as Production in the local rehearsal stack before QA took Docker over (results below). No file of Opus's was edited.

Severity: **blocker** = must not go to Azure; **major** = fix before anyone but the PO is invited; **minor** = fix soon, not a gate; **nit**.

## Verdict

No blocker. The flow is correct and matches ADR-022 section 2. Two major findings, both about availability of sign-in under abuse and about one item of section 2 that is not built; neither lets anyone in who should not get in. The security-critical order (state consumed before any Google call, binder compared in constant time, admission before any row is created, new session at sign-in) is right and is pinned by tests.

## What I checked and found correct

- **Login CSRF, replay, single use.** The state row is consumed with `consumed_at` as a concurrency token (`IdentityDbContext.cs`, `GoogleSignInEndpoints.cs:188-199`), before the binder compare, so a wrong binder burns it. Tests cover the second callback, two concurrent callbacks, a foreign or missing binder and an expired state, each with zero calls to the fake (`GoogleSignInTests.cs:241-316`).
- **Open redirect.** `Location` is a constant plus a closed outcome code (`GoogleSignInEndpoints.cs:177`); start accepts only `{"landing":"home"}` with unknown and duplicate members refused (`:46-55`, tests `:127-141`). The return path never reaches the server.
- **Redirect address** comes only from configuration; the test sends a spoofed `Host` and `X-Forwarded-Host` (`GoogleSignInTests.cs:62`).
- **Session fixation.** The callback ends in the existing `SignInAsync`, which revokes the carried session; a test asserts it (`:186`).
- **Token validation.** RS256 only, both issuer strings, audience, `azp`, `exp` and `iat` required, nonce in constant time, subject pattern, app clock (`GoogleOidcProvider.cs:131-170`). Eighteen failing shapes are tested, including `alg:none`, HS256 signed with the public key and a wrong key under the right `kid` (`GoogleSignInTests.cs:349-369`).
- **Admission order** is the ADR's: unverified email, invite list, school account, closed account, then create (`GoogleSignInEndpoints.cs:210-218`); the school-account test proves it runs after the invite check (`:422`).
- **Startup refusals** for every key in section 2, each asserting the value is not in the message (`ProductionStartupTests.cs:33-60`).
- **Logs.** Outcome and reason codes only (`GoogleSignInEndpoints.cs:172,176,251`; `GoogleOidcProvider.cs:177`); the Trace canary plants email, subject, name, client secret, code, state, nonce, challenge, binder and session cookie across four outcomes (`LogPipelineCanaryTests.cs`, new class).
- **Conformance, observed on a running build** (API image built from this tree, Production, fresh `tether_live` database, my compose variant with the same variable names as the Bicep): it starts, logs "Google sign-in is on; the invite list has 1 entries", and `infra/scripts/smoke.sh` passes probes 1 to 6: 401 `unauthenticated` on `/dev/login`, `{"google":true,"devLogin":false}`, the pinned URL with the configured redirect address, binder cookie attributes, 302 with the exact relative `Location` through the Next proxy, binder expired. A PFX made by `set-google-signin.ps1` loads with `KeyRingSetup.Load`'s exact call on Linux.

## Findings

| # | Sev | Where | Finding | Suggested fix |
|---|---|---|---|---|
| 1 | major | `Google/SignInLimiter.cs:57-68`; `GoogleSignInEndpoints.cs:160-166,293-297`; test `GoogleSignInTests.cs:488-493` | **The no-binder bucket does not protect real returns from Google.** A callback counts as "bound" when it carries ANY well-formed 43-character cookie value. A flood of forged callbacks with random cookie values therefore skips the 30-a-minute unbound bucket, gets a fresh per-binder partition each time, and drains the 300-a-minute global callback bucket; real returns then get `rate_limited`. The test only floods WITHOUT a cookie, so it passes while the bypass exists. This is the callback twin of residual risk 1 and it makes S1.16 worse than the ADR says. | Charge the global callback bucket only after the state row was found, consumed and the binder matched (the requests that go on to call Google). Everything before that costs one primary-key read; put those under a separate, larger "unmatched" bucket. Add a test that floods with random binder values and then completes a real sign-in. |
| 2 | major | `Tether.Host/Program.cs` (nothing added); ADR-022 section 2, "Limits" | **The Run A measurement of the forwarded-header chain is not built.** Section 2 asks for a one-off, content-free log of the `X-Forwarded-For` entry count and whether each entry is private or public. Nothing in the tree reads that header. Without it Run A cannot give the Lead what R6 needs to rule on trusted hops before anyone else is invited. | A small middleware or a line in the sign-in callback, logging counts and private/public flags only, never a value; a test that a planted address does not reach the log. |
| 3 | minor | `Google/SignInLimiter.cs:46-55,57-68` | The per-binder partition is created BEFORE the global permit is taken, so every request with a new random cookie value adds a limiter partition that lives about a minute, with no bound from the global bucket. Memory growth is limited only by how fast requests arrive (the API has 0.5 GiB). | Take the global permit first, then the per-binder one. Combine with finding 1. |
| 4 | minor | `Google/GoogleOidcProvider.cs:118` | A token response with NO `scope` member is accepted. Section 1 says the granted scope must be exactly the three sign-in scopes. Google always sends it [A], so this is strictness, not a hole; no test covers the absent case. | Treat an absent `scope` as `token_scope_unexpected`, or record in `auth.v1` why absence is accepted; add the case to `BadTokens`. |
| 5 | minor | `Google/GoogleOidcProvider.cs:53-60` | When the JWKS cache has expired and the refetch fails, the old keys keep being trusted with no upper limit. A key Google withdrew stays valid for as long as the fetch fails. (The token comes straight from Google over TLS, so the signature is defence in depth.) | After the 24-hour ceiling return no keys (`jwks_unavailable`), or keep stale keys for one bounded grace period. A test with the fake JWKS failing. |
| 6 | minor | `GoogleSignInEndpoints.cs:220-245` | A new user row is saved before `SignInAsync`. If the session insert fails, the outcome is `provider_unavailable` but a user row exists, so "created: nothing" is not strictly true for that outcome. | One transaction around the user insert and the session insert, or state the exception in `auth.v1`. |
| 7 | minor | `docs/API_CONTRACTS_AUTH.md:23`; `GoogleSignInTests.cs:338-344` | The contract says other methods on the callback answer 405. The test accepts 405 OR 401, and for an anonymous caller the fallback policy most likely answers 401 (the same effect the Lead just corrected for `/dev/login`) [A: not run]. A test that accepts two answers pins neither. | Say in the contract what an anonymous caller gets, and assert that one value. |
| 8 | minor | `web/src/components/SignInView.tsx:100-118,160` | After `navigate(url)` the button stays disabled with "Opening Google...". If the student presses Back at Google, the browser can restore the page from its back-forward cache in that state: no way to try again without a reload. | Reset `googleBusy` on `pageshow` when `event.persisted`. A unit test for it. |
| 9 | nit | `web/src/components/AuthProvider.tsx:88` | The ADR's return-path rule is "no `//`"; the check refuses `//` only at the start. `/a//b` is still same-origin, so this is wording, not risk. | Either refuse `//` anywhere or align the ADR sentence. |
| 10 | nit | `Google/SignInLimiter.cs:14-18`; `Program.cs:97-102` | The five new `RateLimiting:Auth*` keys are not in the list that warns at startup when a limit is raised above its shipped default outside Development (N-05). | Add them to that list, or log the same warning from the limiter. |
| 11 | nit | `GoogleSignInEndpoints.cs:84-91` | Expired states are loaded as tracked entities and deleted in one batch; one concurrent consume fails the whole batch (caught, retried by the next start). | `ExecuteDeleteAsync` on the same filter: one statement, no concurrency token involved. |
| 12 | nit | migration `M010_GoogleSignIn.cs:86-101` | `Down` recreates the UNIQUE email index, which fails once two users share an address. | Leave the index non-unique in `Down` and say why. |
| 13 | nit | `LogPipelineCanaryTests.cs` (new class) | The sentinels do not include the ID token itself or the derived PKCE verifier, though the summary names the ID token. | Have the fake expose the last ID token it signed and add both. |

On a Windows developer machine it may not work with the XML key encryption [A]; Development normally has no certificate, so this only matters if someone sets one locally. | A comment, or skip the flag on Windows. |

## Would the tests catch a regression?

Mostly yes: the callback order, the token rules, admission and the startup refusals are each asserted with "nothing was created" counts, and the zero-calls-to-the-fake assertions pin "state before Google". Gaps, in order of value: the random-binder flood (finding 1); the global start and callback buckets (only per-binder, unbound and the live-state cap are exercised, `GoogleSignInTests.cs:474-506`); JWKS unavailable and token-endpoint timeout paths; a token with `nbf` in the future; the exact method answer (finding 7). The web tests cover each outcome state and the proxy 302; I did not see a test for the back-forward cache case.

## Not verified

- I did not run `dotnet test`, vitest or Playwright for Opus's half; QA or the Lead should.
- The Data Protection path with a previous certificate and the restart round trip are covered by `KeyRingTests`, which I read but did not run. In the rehearsal I only saw that swapping certificates without a previous one logs "Unable to retrieve the decryption key" and the API carries on with a new key, which is the behaviour C1 was written to avoid.
- Findings marked [A] are from reading, not from a run.
