### A. Audio ticket

| ID | Sev | Finding | Fix to contract text |
|---|---|---|---|
| C-01 | High | The ticket rules are incomplete. "Single use, 30 s, bound to user, session and Origin" is stated, but the contract does not say how single use is enforced, when it is consumed, or what else invalidates it. Without that: two sockets racing on one ticket can both succeed, a ticket minted before a pause or stop still works afterward, and a ticket minted before logout still works afterward. | Add to section 1 or 4: "Ticket is 256 bits from a CSPRNG. Only its SHA-256 is stored. Consumption is one atomic compare-and-delete (or `UPDATE ... WHERE used_at IS NULL RETURNING`) done when `hello` is received, and it is consumed even if later checks fail. At consume time the server re-checks that the session is `Active`, that it is owned by the ticket user, that the cookie session behind the upgrade is not revoked, and that the Origin equals the Origin bound at issue. At most one outstanding ticket per session, so a new issue invalidates the old one. Pause, stop, delete and logout invalidate outstanding tickets. The ticket is never logged, never put in a URL, and never echoed in an error or `ack`." |
| C-02 | High | Authentication of the audio socket is ambiguous. Section 1 says "single-use ticket + Origin check + session ownership + Active". It does not say whether the session cookie must also be present on the upgrade. If the ticket alone authenticates, a stolen ticket (within 30 s) works from any client that sets any Origin header, since non-browser clients can send any Origin. | State: "The upgrade requires a valid session cookie AND the ticket. The cookie user must equal the ticket user. The path `{id}` must equal the ticket session." Also state that `/audio-ticket` responses carry no CORS allow headers (no `Access-Control-Allow-Origin`), so a foreign site cannot read a ticket. |
| C-03 | Medium | The Origin check on the audio socket is described as close code 4403 after the handshake. That accepts the upgrade from a hostile Origin and lets it hold a connection open. | "Origin is checked before the upgrade completes. A bad or missing Origin gets HTTP 403 with no upgrade. Origin comparison is exact, ordinal, against a configured allowlist (this also closes N-11). A missing Origin is rejected on all three channels; non-browser clients are not supported on the production endpoints." Keep 4401/4409 for post-upgrade failures. |
| C-04 | Medium | There is no pre-authentication limit on the audio socket. An unauthenticated peer can open sockets and never send `hello`, or send a huge first message. | Add: "`hello` must arrive within 5 s and be at most 1 KB, otherwise the socket is closed. Binary frames before a valid `hello` close the socket. Max text message 4 KB, max binary frame is a fixed size computed from the audio format (for example at most 250 ms of PCM plus the 12-byte header). Oversize closes with 1009." |
| C-05 | Medium | Ticket issuance has no rate limit and no per-session cap, and failed `hello` attempts have none either. Issuance is cheap but is an oracle for the session state (409) and a way to churn the store. | "`POST /audio-ticket` is limited per user (for example 6/min) and per session. Failed `hello` attempts are counted per user and per IP and feed the existing 429 limiter. Failure responses for bad, expired, used and foreign tickets are identical (same close code 4401, no distinguishing text)." |

### B. Hub and WebSocket Origin / CSRF (F-04)

| ID | Sev | Finding | Fix to contract text |
|---|---|---|---|
| C-06 | High | The hub only authenticates at connect. A long-lived SignalR connection keeps working after logout, session revocation, absolute expiry (F-01/F-02), user deletion, or `DELETE /sessions/{id}`. This silently undoes the M1 session revocation work for the most sensitive stream. (SignalR authenticating once per connection is my understanding of the framework; confirm on the pinned version.) | Add to section 3: "A hub connection is bound to the cookie session id (`sid`). The server aborts the connection when that session is revoked or expired, and in any case re-validates it at least every 60 s. Maximum connection lifetime is 1 hour; the client reconnects with `Join`. `DELETE /sessions/{id}`, session `Stopped`/`Failed` for deletion, and user deletion remove the connection from the session group and send nothing further." Same rule for the audio socket: close with 4401 on revocation. |
| C-07 | High | CSRF/CSWSH layers are not specified for the hub. F-04 is named but the contract only says "Origin check on negotiate and upgrade". SignalR has HTTP fallbacks (SSE, long polling) that carry cookies and would need their own checks. The `Join` method is the real authorization point and is not stated as per-invocation. | Add: "Hub transport is WebSockets only; SSE and long polling are disabled. Origin check (C-03 rules) applies to negotiate (POST) and to the upgrade (GET). `[Authorize]` is on the hub class. Every hub method re-resolves the session through the user-scoped query on each call, not only on `Join`. Group names are server-built `session:{id}` and a client can only join through `Join`. No client-supplied group names exist." Add a contract test: cross-origin negotiate, cross-origin upgrade, missing Origin and a `null` Origin all fail. |
| C-08 | Medium | SameSite value for the session cookie is not restated for the new channels. The M1 cookie is `__Host-` prefixed, which helps, but WebSocket handshakes are same-site GETs from sibling subdomains. | State that the web app and API are served from origins covered by one exact allowlist, and that the cookie is `SameSite=Strict` (or document why Lax is required, for example for the OAuth return). Record this in the F-04 test. |

### C. seq, replay and cross-user exposure

| ID | Sev | Finding | Fix to contract text |
|---|---|---|---|
| C-09 | Medium | The replay path takes a client-supplied `lastSeq`/`sessionId`. The text says a foreign join "fails identically to a missing one" but does not require the replay query itself to be scoped. A later refactor that queries `events WHERE seq > @lastSeq` without the user filter would leak across users. `seq` is per session, so cross-user collisions are likely and invisible in single-user tests. | "Every event read (hub replay, `GET /transcript`, summary, catch-up) is keyed by `(userId, sessionId)` through the user-scoped query, never by `seq` alone. `lastSeq` greater than `currentSeq` or negative returns the current state with an empty replay, not an error that reveals the real count to a non-owner. `limit` has a server maximum." Add a two-user contract test with overlapping `seq` values and identical segment ids. |
| C-10 | Low | "Gap-free `seq` assigned in the same transaction" implies a per-session counter row that serializes writers. A database sequence would leave gaps on rollback and break the guarantee. This is a correctness and availability concern, and a slow writer can stall finals. | State that the implementation uses a per-session counter row updated in the persisting transaction (not a DB sequence), with an explicit max event rate so a flood cannot hold the row lock. Note `seq` is int64 and the client JSON must treat it as a string or bounded number. |
| C-11 | Low | In-memory partials ("latest partial replayed on join") are transcript text outside the database. | State that partials are held per `(userId, sessionId)`, cleared on stop, pause (see C-12) and delete, and never logged or persisted. |
| C-12 | Medium | `citations[{segmentId, startMs}]` and `catchup` citations come from model output. A manipulated or injected output could cite a segment id from another session or a nonexistent one, and `segmentId` is `seg_{n}`, guessable and not globally unique. | "The server validates every citation against the same session before emitting or storing; invalid citations are dropped. `segmentId` is only meaningful together with `sessionId`." |

### D. Consent gating and pause/stop semantics

| ID | Sev | Finding | Fix to contract text |
|---|---|---|---|
| C-13 | High | Consent is defined only at session creation and the contract does not make the server authoritative on its content. `consent:{acknowledged:true, textVersion}` is client-asserted; the server could store any `textVersion`. SEC-008's per-course permission attestation, and SEC-007's lifecycle events (grant, pause, resume, stop, revoke), are absent. The `audio-ticket` 403 `consent_required` has no defined condition because consent is already recorded at creation. Nothing here clears G1. | In section 2: "`textVersion` must match a server-side registry of published versions; unknown or retired versions return 403 `consent_required`. The text of each version is labeled DRAFT until G1 is cleared by the Product Owner and counsel. Session creation additionally requires a current per-course recording-permission attestation (SEC-008) and returns 403 `consent_required` otherwise. Each of start, pause, resume and stop appends a row to the append-only consent event table in the same transaction as the state change (SEC-007). `audio-ticket` returns 403 `consent_required` if the stored consent version has since been retired." Also state that no real audio provider is reachable while the consent text is DRAFT (a startup guard that refuses a non-replay `ISpeechToTextProvider` unless G1 is recorded as PASS in configuration set by a human). |
| C-14 | High | Pause and stop have an in-flight audio hole. The server keeps a ~5 s channel and applies backpressure, and the client has a 30 s ring buffer. After `pause` or `stop`, buffered frames could still be forwarded to the STT vendor and produce finals for audio the student believed was no longer being recorded. The contract says only "Paused accepts no audio". | Add: "On pause or stop the server atomically (a) sets the state, (b) discards every unsent frame in the server channel, (c) rejects frames received afterward, and (d) closes or flushes the vendor stream. Frames whose `captureOffsetMs` lies after the pause/stop instant are discarded, never transcribed. The client discards its ring buffer on pause and stop and does not replay it after resume. No finals are persisted for discarded audio. Test: send frames, pause, assert zero finals for later offsets." Because the 5 s channel is by design, say plainly in student-facing copy that a few seconds of already-sent audio may still be processed; PO/counsel to confirm wording. |
| C-15 | Medium | The audio socket accepts `pause`/`resume`/`stop` JSON that "mirrors REST". Two control paths for one state machine race, and a `resume` over the socket could bypass REST checks (state, consent version, concurrency cap). | "The audio socket accepts only `pause` and `stop` (reduce-only). `resume` is REST only and requires a new ticket for a new socket. On any state mismatch REST wins and the socket is closed." |
| C-16 | Medium | The indicator is defined as `session.state` from the hub ("source of truth for the visible recording indicator"). SEC-009 requires the indicator to reflect actual client and server state. A server `Active` with a dead mic, or a server `Paused` with a still-live mic track, would show the wrong thing. The second case is a privacy failure. | "The indicator is computed from both the server state and the local `MediaStreamTrack.readyState`/`enabled`. On pause and stop the client stops the track before showing Paused/Stopped; if the two disagree the UI shows a prominent mismatch warning and stops capture. Hub disconnect shows 'not connected, audio not being saved' status rather than leaving a stale 'Recording'. Announced via a live region." |
| C-17 | Medium | Unattended recording limits are loosely defined. A 10-minute no-heartbeat abandon and a 3 h cap are defaults, but heartbeat is undefined (hub `Ping`? audio frames?), and `Paused` sessions are not capped. A closed tab with an open mic path is the risky case. SEC-011 asks for idle auto-end. | "Heartbeat is the hub `Ping` AND/OR audio frame arrival (define which). Idle with no audio frames for 60 s while `Active` produces a server `gap` and, after 5 min, an auto-pause. `Paused` auto-stops after 30 min. Hard cap applies to total elapsed time including paused. Values are configuration owned by devops but the maximums are fixed in this contract." These numbers are my proposal; PO to choose. |
| C-18 | Low | One-recording-per-user is a 409 `invalid_state` but concurrency (two requests at once) and multiple audio sockets for one session are not addressed. | "Enforce with a unique partial index on `(user_id) WHERE state IN ('Active','Paused')`. A second audio socket for the same session is rejected with 4409." |
| C-19 | Low | `captureOffsetMs` is client-supplied and also the basis for timecodes and citations. | "Server derives timecodes from accepted sample counts; `captureOffsetMs` is advisory only and used to detect gaps." |
| C-20 | Medium | `speaker?` on partial and final events can carry diarization labels for instructors and classmates. That is data about third parties (bystander privacy, open risk 5 in SECURITY.md). | Mark `speaker` as optional and off by default in M2, and add to the G1 legal checklist; no voice-identification across sessions. |

### E. Deletion of derived data

| ID | Sev | Finding | Fix to contract text |
|---|---|---|---|
| C-21 | High | `DELETE /sessions/{id}` says "deletes transcript and all derived data" without enumerating it or covering in-flight work. Likely survivors: summary revisions, catch-ups, notes, mock/real export records, in-memory partials, queued summarizer jobs that complete after the delete and re-insert rows, hub group members, caches, and logs. Deleting an `Active` session is also unspecified. | Replace with: "Deletion of an Active/Paused session first stops it (C-14), closes its audio socket and removes hub members, then hard-deletes in one transaction: transcript events and corrections, summary revisions, catch-ups, notes, export records, citations, and ephemeral partials. Pending AI/summary/export jobs are cancelled, and every job writes with a check that the session row still exists (FK with `ON DELETE CASCADE` plus a check in the writing transaction) so a late job cannot recreate data. Consent event rows persist as non-content metadata only (no title, no text) per SEC-014. Course deletion and account deletion cascade the same way. Data already sent to Google Docs, and data held by STT/Anthropic under their retention terms, is NOT deleted by this call and must be stated in the disclosure (SEC-017). Backup expiry SLA is <= 30 days. An audit event with no content is written." Add tests: delete during an in-flight summary, delete of an Active session, delete then `GET` returns 404 on every sub-resource. |
| C-22 | Low | No export/deletion confirmation semantics for the mock exporter: `export/doc` 202 has no status resource. | Out of scope for M2 security except: the mock exporter must not write anything outside the database, and exports are owner-scoped on read. Note it so the M3 Google exporter does not inherit a gap. |

### F. Log canary

| ID | Sev | Finding | Fix to contract text |
|---|---|---|---|
| C-23 | High | Section 6 has a single line: "a sentinel transcript string never appears in logs (F-08)". That is too weak to carry SEC-027 and ADR-017's gate. It does not say which sinks, what level, which paths (failure paths are where text leaks), or that it blocks merge. m1-rereview reports `LogError(ex)` in `Program.cs:133-134` still unchanged; an exception that embeds a row value would pass a happy-path canary. | Replace with: "Log canary test, required status check before any code that persists or relays transcript text merges. It uses a unique canary string in (1) fixture audio/finals via `ReplaySttProvider`, (2) a lecture phrase that also appears in an injected exception message, (3) a summary or catch-up, (4) a request body and a rejected request body. It runs with all log categories at Trace, EF sensitive-data logging on, and OpenTelemetry/exporters attached to in-memory sinks. It asserts the canary is absent from every log record including scopes and exception text, traces, metrics labels, ProblemDetails bodies and hub `error.detail`. Also run with fault injection: STT failure, AI schema failure, DB failure. Also asserts the audio ticket value and cookie value never appear. A global exception handler logs exception type and id only (no `ToString()` of exceptions that wrap input)." |
| C-24 | Medium | The `error {code, detail}` hub event and ProblemDetails `detail` may carry free text from exceptions or model validation errors that echo input. | "`detail` is chosen from a fixed server vocabulary keyed by `code`. Never exception text, input echo or model output." |

### G. Rate limits, DoS and cost on ingest

| ID | Sev | Finding | Fix to contract text |
|---|---|---|---|
| C-25 | High | Ingest limits are only implied. The contract has no maximum frame size, no maximum byte rate, no per-user socket cap, and no STT minutes budget. A client can send audio faster than real time, send huge frames, or run many sockets, burning provider cost (SEC-037) and server memory. Also, the server buffer is "~5 s" but unbounded memory per socket is not ruled out if frames are large. | Add an "Ingest limits" subsection: max binary frame size (derived from format; C-04), accepted audio rate at most 1.1 x real time measured over a sliding window (excess is dropped and reported as `error{code:"rate_limited"}`, repeated violation closes with 1008), 1 audio socket per session and 1 recording session per user (C-18), per-user daily STT minutes budget with a graceful `stt.status Degraded` / stop at the limit, a global kill switch, and `gap` accounting for dropped data. The numbers are config, but the existence of every limit is part of the contract. Memory per session is bounded by the 5 s channel cap. A load test returning the documented codes goes in section 6. |
| C-26 | Medium | Hub and REST abuse limits are missing for M2 endpoints: `lost-track` (AI cost), `Join` replay (up to 5000 events per call), `GET /transcript` page size, `Ping` rate, hub message size, connection count per user. m1-rereview N-04 (IPv6 /64) and N-09 remain open and the new surface depends on them. | "Hub `MaximumReceiveMessageSize` 4 KB. Max 3 concurrent hub connections per user. `Join` limited to 10/min per session. `lost-track` limited to 6/min per session and a per-session AI call budget, with the extractive result always returned. `limit` maximum on every list. IPv6 limiter keys on /64 (N-04). Architecture test banning `ExecuteUpdate`/`ExecuteDelete` on user-owned sets lands before M2 persistence code (N-09)." |
| C-27 | Low | Replay cap of 5000 events per `Join` is an amplification vector: one cheap call returns a large payload to a peer that reconnects in a loop. | Cap at a smaller default (for example 500) with `truncated:true`, and count `Join` against the limiter. |

## Suggested contract tests to add to section 6
1. Ticket: replayed, concurrent double-consume, expired, wrong user, wrong session, wrong Origin, post-pause, post-logout, no cookie.
2. Socket pre-auth: no `hello` within 5 s, oversize text, oversize binary, binary before `hello`.
3. Hub: cross-origin negotiate and upgrade, missing and `null` Origin, SSE/long polling refused, connection dropped after logout and after delete.
4. Two-user overlap on `seq` and segment ids across replay, transcript, summary and catch-up.
5. Pause and stop discard buffered frames, no finals for later offsets.
6. Delete during in-flight summary and while Active; every sub-resource 404 afterward.
7. Canary run per C-23 including fault injection.
8. Rate limits: audio faster than real time, frame size, socket cap, `lost-track`, `Join`, ticket issuance.
