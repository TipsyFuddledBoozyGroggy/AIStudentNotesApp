## Release position

- **Critical 0, High 2, Medium 11, Low 11, Info 4 (28 findings).**
- Recommendation: **do not freeze yet.** Freeze after the "before freeze" list below is folded in. Two of the items (CV-01, CV-02) are contradictions with the frozen `syllabus.v1` and with PO-9n that would be hard to fix after freeze. Five items change wire shape (CV-08, CV-10, CV-11, CV-19 optional, CV-02 optional). All the rest are text, state-machine or data-design corrections.
- After those edits I would support a **conditional freeze for mock/fake-Google implementation only**, same posture as `syllabus.v1`. This says nothing about a real Google account, real student data or production.

## What the draft already gets right (do not weaken)

POST-only start routes; PKCE S256 always explicit; server-built URL with a pinned parameter set and exact redirect; state hashed, single use, 10 minutes, session or binder bound; sign-in with no data scope; `iss`+`sub` as identity, never email; connect `sub` must equal sign-in `sub`; no Google write at callback; landing is a route key, not a URL; host allowlist for egress; refresh token envelope-encrypted with AAD; no token, `sub`, calendar id or remote event id in any schema (tested); preview then confirm then plan recompute with zero writes on mismatch; `needs_date` items cannot be entries; per-occurrence intents with deterministic ids; description is a fixed template (no notes/snippets); markers explicitly "not a security boundary" (corrects the proposal); never recreate a student-deleted event (PO-9a); removal before revocation and row deleted even if revocation fails; unknown/duplicate JSON members are `400`; ownership chain `404` before idempotency, rate limits and state; separate `schedule_write` bucket.

| **CV-03** Medium | 9.3 drift check, 13.1, 10 item 6, CAL-14 | Three defects behind the promise "never overwrite a student edit". (a) **Update semantics.** The contract picks `get` then `update` (not `patch`). `events.update` is a PUT that replaces the whole resource (**verify**; general Google behaviour). The text compares only "summary, start, end, description, reminders, status". A student who added a location, Meet link, colour, attachment, attendee or visibility change is not seen as "edited", and an `update` that sends only managed fields **wipes those additions**. (b) **TOCTOU.** Between the drift `get` and the `update` the student can edit; nothing in the text requires `If-Match`/etag on the write (13.3 mentions `412` only "if used; unverified"). The student's edit is overwritten with no signal. (c) **False positives.** The fingerprint is of what Tether *sent*; Google normalises (adds `end.timeZone`, reminder defaults). If the comparison is wrong, **every** event reads as `edited_in_google` after the first `get`, `edited_in_google` is terminal, and the whole schedule silently stops updating (a stale exam date). | (a) Normative: the update body is the **full resource returned by the `get` with only the managed fields substituted**, never a freshly built partial body; unmanaged fields round-trip. (b) Send `If-Match: <etag from the get>` on `update` and `delete`; on `412` re-`get` once and re-evaluate; if T7 shows `If-Match` unsupported, require a second cheap check (`updated` unchanged immediately before the write) and record the residual window in the register. (c) Compute `last_written_fingerprint` and `remote_etag`/`remote_updated_at` **from Google's response to our insert/update**, not from the request; compare canonical subsets of two Google-normalised views. Treat an `etag` change with an unchanged canonical subset as "unchanged, refresh etag", not "edited". Add fake-Google cases: normalisation of `end.timeZone`, student adds location, edit between get and update. **Before freeze (text).** |
