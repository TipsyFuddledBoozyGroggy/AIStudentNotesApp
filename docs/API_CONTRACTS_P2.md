## 2. Conventions (inherited, plus the normative rules below)

Base path `/api/v1`, session cookie plus Origin check, user-scoped: a foreign or missing id is `404 not_found`, never 403. Errors are RFC 9457 ProblemDetails with a stable `code` (`syllabus-problem.schema.json`; the lecture.v1 codes plus section 9). `detail` is a fixed server string per `code`, never exception text, model output, document content, a filename or a detected file type; `errors` keys are field names and its values come from a fixed vocabulary that never echoes the rejected value. Lists are `{items, nextCursor}` with `?cursor&limit`, server maximum 200. `ETag` is the opaque weak tag; `If-Match` is required on item writes (`428 precondition_required` when absent, `412 precondition_failed` on mismatch; lecture.v1 codes, not `409 conflict`).

Dates the student reads are **wall-clock**: `YYYY-MM-DD`, `HH:MM` and an IANA zone id (`America/New_York`). No UTC and no offsets appear anywhere except instants (`createdAt`, `syncedAt`). UTC conversion happens only at a real Calendar write, in a future provider's code, and is out of scope. All-day items carry no time and do not shift.

### 2.1 Request handling (normative)

- **Unknown members are rejected.** Request DTOs are separate from entities and are never bound onto them. Unknown JSON members, and duplicate member names, are `400 validation_failed`. The duplicate-member option must be set on the **serializer options actually used for typed binding** (`JsonSerializerOptions.AllowDuplicateProperties = false` plus `UnmappedMemberHandling = Disallow`, .NET 10), not only on `JsonDocumentOptions`: with default serializer options a duplicate key in a `Dictionary<string,T>` (`itemEtags`, `itemRevisions`) is silently collapsed, last one wins. `SyllabusPreFreezeTests` exercises typed binding through `JsonSerializer.Deserialize` with a negative control showing the default collapses; the real minimal-API binder configuration remains a **required server test**. Posting any read-only field (`origin`, `confidence`, `flags`, `syncState`, `userId`, `courseId`, `syllabusId`, `itemKey`, `revision`, `etag`, `edited`, `snippet`) is `400`, never silently ignored. Every request schema has `additionalProperties: false`; red-team fixtures `*--readonly-*` exist for each.
- **Evaluation order** for every route, so no error leaks the existence or state of a resource the caller does not own: (1) authentication `401`; (2) Origin/CSRF `403 csrf_failed`; (3) syntax: `Idempotency-Key` well-formed, else `400`; `If-Match` present, else `428`; and the **canonical-id form check of every path, query and body id (R3-14)**, so a malformed id is always `400` before any lookup and never ordered after a `404`; (4) **ownership chain** `(userId, courseId, syllabusId, itemId)` through user-scoped queries, failing as `404 not_found`; (5) **idempotency lookup** by `(user, method, route template, key hash)` (see Idempotency-Key below): a hit with a matching fingerprint is a replay and skips steps 6-9, a hit with a different fingerprint is `400`, a miss continues; (6) per-user and per-route limits `429 rate_limited` and quota `409` (`extraction_in_progress`, `syllabus_limit_reached`), decided from counters only, before any body is read; (7) body read with streaming caps (`413`, `415`); (8) validation `400`; (9) state `409` / precondition `412`. A caller who does not own the course therefore never sees `409`, `413`, `415` or `429` caused by someone else's data. The key lookup is by header only and needs no body, so a multipart create can be recognised as a retry before any file byte is read; the fingerprint comparison for a multipart create happens at step 7 (see below).
- **Media type of JSON bodies (Lead decision 62).** Every JSON request body, including item `PATCH`, must be sent as `application/json` (parameters such as `charset=utf-8` are allowed). `PATCH` has JSON merge-patch *semantics* (present member = set, `null` = clear where allowed, absent = unchanged) but **`application/merge-patch+json` and `application/json-patch+json` are not accepted**: `415 unsupported_type` with the neutral wording of section 9. A wrong or missing `Content-Type` is `415` at step (7), after ownership and quota checks.
- **`If-Match` (Lead decision 63).** Exactly one `If-Match` header field is required on item `PATCH`, `DELETE` and `decision` (missing or blank: `428 precondition_required`; more than one field, or a comma-separated list, which the host splits into several values: `400 validation_failed`). Etags are opaque **weak** validators (`W/"..."`, an HMAC over resource id, row version, creation time and restore epoch) and are compared in constant time on the opaque value, ignoring the `W/` prefix and the quotes, so a client that echoes the `ETag` response header verbatim is correct; the strong form of the same value is also accepted. **`If-Match: *` is not accepted**: it is compared as one opaque string, never matches, and the answer is `412 precondition_failed` (after the ownership checks, so a foreign resource stays `404`), as is any other single value that is not the current tag. A list of etags (`"a", "b"`) is never accepted, not even when it contains the current one: it is `400`. There is no unconditional write.
- **Body caps for JSON routes** (checked while streaming, `413`): 16 KB for `decisions`, `calendar-sync`, `calendar-sync/remove`, item create and PATCH, decision; 1 MB for pasted-text create (50,000 code points can reach about 600 KB with `\uXXXX` escaping). The multipart `metadata` part is 4 KB. NUL is checked **after** decoding (a UTF-16 file legitimately contains 0x00 bytes before decoding).
- **Nested ids.** An item id is valid only within the syllabus in the path, and a syllabus id only within its course and owner. A body id (`itemEtags` and `itemRevisions` keys, `itemIds`, `existingSyllabusId`) that is not in that syllabus gets the same outcome as a nonexistent id: `404` for a path id, per-item `not_found` inside a `200` result. Foreign, nonexistent and other-syllabus ids are indistinguishable in status, body and (as far as practicable) timing. Child rows carry `user_id` and are filtered by the global query filter. Lookups for duplicates are `(userId, courseId, contentSha256)` and the unique index includes `user_id`. A route-by-route test table (every route, two users with overlapping ids, plus a same-user mismatched parent) is required (section 12).
- **One canonical id form (R2-05).** Every id has exactly one canonical text form (decision 2: lowercase, hyphenated, optional 3-letter prefix; for a GUID id, `Guid.ToString("D")`). The server compares only canonical text: an id that does not round-trip (`ITM_...`, braces, `urn:uuid:`, missing hyphens, surrounding whitespace or a trailing newline) is **rejected as `400 validation_failed` in a path, a query string and a body** before any lookup, so it can never alias a real id, never yields a second key for the same item inside `itemEtags` or `itemRevisions`, and a malformed id and a nonexistent id are told apart only by form, never by whether a row exists. After decoding, the server de-duplicates object keys again (defense in depth). The schema patterns accept lowercase hyphenated text and cannot tell a GUID-shaped id from another opaque token, so the parser round-trip check is a required server test. `itemRevisions` values are integers 1 to 2147483647.
- **CSRF/Origin** apply to every state-changing route, **including the multipart upload and every DELETE**: exact ordinal Origin match, a missing Origin is rejected, and a required custom header is checked. `multipart/form-data` is a CORS-safelisted type, so the Idempotency-Key header being "non-simple" must not be relied on as the defense.
- **Ids** are at least 128 bits from a CSPRNG (or GUID/ULID) and never sequential. `itemKey` is an idempotency basis only; no endpoint accepts it as an identifier.
- **Idempotency-Key** (format `syllabus-common.idempotencyKey`, 8-128 URL-safe characters, else `400`). Scope is `(user, method, route template, key)`, with a unique index on `(user_id, method, route_template, key_hash)`; the stored fingerprint covers the concrete path (so the `syllabusId`), a canonical hash of the body and, for multipart, the file hash plus metadata. Reusing a key with a different fingerprint is `400 validation_failed`. Keys are kept 24 hours; the stored record holds ids and hashes only, never titles or a response body. **Multipart hashing:** the fingerprint of a multipart create is **HMAC-SHA-256 with a server-held key (R3-10; never a plain hash, because the tombstone outlives the syllabus and a plain hash of a document would let anyone with database access test whether a given file was uploaded)** over the method, route template, concrete path (so the `courseId`), the canonical JSON of the `metadata` part (sorted members, normalised) and the SHA-256 of the file part (an in-memory intermediate, never stored), computed on the stream in the same single pass that writes the bytes to the ephemeral volume under the 10 MB cap (no second read, no in-memory buffer). Replay detection for a create therefore completes at evaluation step 7, after the body has streamed and been hashed and before validation. **Candidate replays:** at step 5 a key lookup that finds a record marks the request a *candidate replay*; for a candidate replay the quota checks `409 extraction_in_progress` and `409 syllabus_limit_reached` of step 6 are skipped (rate limits `429` still apply), and `409 duplicate_syllabus` is decided only at step 9 on a miss. A retry with the same key and fingerprint while the original job is running therefore gets the replay (`202`, current representation, `Idempotency-Replayed: true`), not `409 extraction_in_progress`; its bytes are discarded after hashing. A different fingerprint is `400 validation_failed`. **Replay semantics:** a replay re-runs authentication, Origin and ownership, then returns the operation's **original outcome** with `Idempotency-Replayed: true`. For creates that is the resource's current representation; for `calendar-sync` it is the original result as produced at `completedAt`, rebuilt from the sync run records. **Replay after delete (one rule, used everywhere in this contract):** returning the original response after the syllabus was deleted is **not allowed**, and the operation is never re-executed. For every route with a `syllabusId` in the path, step 4 already answers `404 not_found`. For create, deleting the syllabus (including cancel) reduces the key record to a **content-free tombstone** (user id, method, route template, key hash, fingerprint hash, expiry; no syllabus id, no content hash, no text) kept until the 24 hour key expiry. A request matching a tombstone (same fingerprint) gets `404 not_found` with the standard body, i.e. the outcome named `syllabus_deleted` internally and indistinguishable on the wire from any other missing resource (there is no `syllabus_deleted` wire code); a different fingerprint is `400`. A late network retry of a create after the student pressed Delete can therefore never silently create a new syllabus within 24 hours; after expiry the key is new. **Current state may differ**: if the student skipped an item after the first call and the client retries the old key, the replayed body still says `created` while the item is `skipped` and its event gone. Clients must treat a replayed body as history and re-read items and events for state. No operation is re-executed on replay.
- **Revision vs ETag.** `revision` is the content revision; it bumps only when content (kind, title, notes, dates, times, zone) changes, and `syncedRevision` refers to it. The `etag` changes on **any** mutation of the item (content, decision, `syncState`) and includes the resource id, so it is never accepted for another item. A stale approve/skip pair from two tabs therefore yields `412` for the loser.
- **Atomicity.** Decision and sync handlers re-check `approved`, `when.status == resolved` and the unchanged `revision` inside the transaction that locks the item rows (`SELECT ... FOR UPDATE` or a concurrency token), never on a value read earlier. Tests race PATCH, decision and sync (section 12).

### 2.2 TextPolicy (normative, one implementation, applied at write time and at every sink)

Every student-entered or document-derived text field goes through one `TextPolicy` on write, from the student path and the AI path alike: `title` (items, syllabus), `notes`, `confidenceReason`, `written.dateText`/`timeText`, `snippet.text`, `snippet.context.text` and pasted `text`.

- **Defined by Unicode general category and explicit rules, not by a character list (R2-02).** The server `TextPolicy` is authoritative. The schema `pattern`s are a **coarse first filter** with the same intent (they enumerate the known ranges and cannot know the Unicode version); every pattern uses the end anchor `(?![\s\S])` and never `$`. Reason: `$` matches before a final LF in .NET and ECMAScript, so `"Exam 1\n"` passed the earlier patterns (verified by the re-review probe). Server regexes also run with a match timeout.
- **Normalization (R2-08 shares it):** Unicode **NFC** (not NFKC: snippets must stay verbatim with the document; compatibility matching is done on a separate matching-only copy, section 8); whitespace runs collapse to one U+0020 (`title`, `dateText`, `timeText`, `confidenceReason`); lines in `notes`, snippet and context are LF-normalized; leading and trailing whitespace removed.
- **Rejected on student-supplied fields (`400 validation_failed`)**, by category: **Cc** (every C0/C1 control, so no NUL, CR, tab, DEL or U+0085; `notes` allows LF only); **Cf** (format characters: U+00AD, U+061C, U+180E, U+200B, U+200E/200F, U+202A-202E, U+2060-2064, U+2066-2069, U+206A-206F, U+FEFF, U+FFF9-FFFB, tag characters U+E0000-E007F, the musical and other supplementary format controls such as U+1D173-1D17A, U+1BCA0-1BCA3 and U+13430-1343F); **Cs** (any unpaired surrogate; paired surrogates are one code point); **Co** (private use, BMP and planes 15-16); **Cn** (unassigned code points, per the Unicode version pinned in the build); U+2028/2029 (Zl, Zp); **variation selectors**: U+FE00-FE0D, U+180B-180D, U+180F and the whole supplement U+E0100-E01EF (an invisible-data carrier like tag characters; U+FE0E and U+FE0F are allowed only directly after a non-space, non-ASCII base, or after a keycap base `0-9 # *`, i.e. inside an emoji sequence, never at the start, doubled, or after whitespace or ASCII letters); **Default_Ignorable_Code_Point** fillers and joiners that have no visible use: U+034F, U+115F, U+1160, U+3164, U+FFA0; the braille blank U+2800 and the object replacement character U+FFFC; the replacement character U+FFFD (a literal U+FFFD is decoding damage and is rejected). **Decoding failures (R3-02):** a lone surrogate escape (`\ud800`, `\udc00`, a reversed pair) or invalid UTF-8 (a 0xFF byte, CESU-8 bytes such as ED A0 80) in a request body does **not** arrive as U+FFFD: System.Text.Json throws on reading the string (`InvalidOperationException` from `JsonDocument`, `JsonException` from typed binding). The server maps every such failure to `400 validation_failed` with the fixed `detail`, never `500`, and never logs or returns exception text (section 9 error hygiene). Handlers should use typed binding; any `JsonDocument.GetString()` use must be wrapped. Each case is a required server test (section 12); and an orphan combining mark (`\p{M}` at the start, after whitespace, or after a line start), or more than 4 consecutive `\p{M}` marks (all blocks, not only U+0300-036F).
- **Whitespace (R2-02):** the check is on `\p{Zs}` and `White_Space`, not only U+0020. A value that is empty after trimming Unicode whitespace is rejected (so a title of NBSP, U+3000 or U+2007 is `400`). Leading and trailing Unicode whitespace is rejected on student fields (and trimmed on document-derived text). Single-line fields reject every whitespace character other than a single U+0020 between words (NBSP, U+3000 and friends inside a title are `400`; they are normalised to U+0020 only in document-derived text). `notes`, snippet and context may contain NBSP inside a line.
- **ZWNJ (U+200C) and ZWJ (U+200D) are allowed only between letters or emoji (R2-03)**, so Persian text (for example "می‌خواهم"), Indic conjunct shaping and ZWJ emoji sequences work. They are rejected at the start or end of a value, doubled, next to whitespace, or after ASCII punctuation; the server checks the neighbours by script and emoji rules (the schema pattern checks only the first four, since it cannot see scripts). LRM and RLM (U+200E/200F) remain rejected as bidi marks; all other bidi controls (embeddings, overrides, isolates U+2066-2069, U+061C) remain rejected. Rationale: the sinks escape, so these are not an injection risk, and rejecting them would make the app fail for students who write in Persian, Hindi or with emoji. This is a deliberate trade-off: a Japanese name that needs an ideographic variation sequence (U+E0100-E01EF) is rejected too (accepted cost; Product Owner may overturn).
- **Lengths (R2-16, Lead decision) are measured in Unicode code points** for every TextPolicy cap: `title` 200, `notes` 500 and at most 10 lines, `snippet.text` 600, `snippet.context.text` 1,500, canonical and pasted text 50,000, `confidenceReason` 200. The server and the database CHECKs count code points. **Only snippet and context OFFSETS stay UTF-16 code units** (the .NET string index, section 4). The schema `maxLength` is validator-dependent (JSON Schema defines it in code points, but some validators count UTF-16 units), so it is a loose upper bound and the server cap is authoritative; a string of 200 astral characters (fixture `textpolicy-astral-200-code-points-title`) is valid and 201 is `400`. Database columns must therefore be sized so that a code-point cap is never tested with a UTF-16-length CHECK.
- **Document-derived text** (canonical text, snippets, AI titles) is **canonicalized by stripping** the same characters rather than failing the whole document (NUL in a pasted `text` is rejected), so the stored value always satisfies the schema. **Stripping is itself a signal (R2-06):** every code point stripped as a tag character, a bidi control or another Cf character (not ordinary U+00AD soft hyphens or a lone BOM at the start) **and every stripped variation selector outside an emoji sequence (including the U+E0100 supplement), U+034F, Hangul filler, braille blank (U+2800) or U+FFFC (R3-08)** is added to `document.hiddenContentRemoved`, which sets `document.hiddenContentDropped: true` and `batchApproveAllowed: false` (schema-enforced); a document with a tag character, a variation selector from the U+E0100 supplement, a bidi override or isolate, or more than 8 stripped format characters also sets `injectionSuspect: true`. **Residual (R3-09, accepted for mock):** U+FE0E/U+FE0F after any non-ASCII base is a one-bit-per-character invisible channel in student titles; sinks escape and the AI never sees student titles. The server restricts them to bases with the Emoji property and keycap bases and rejects them after whitespace (including NBSP and U+3000 in `notes`).
- **Schema patterns are a UTF-16-engine filter (R3-07).** The astral exclusions are written as UTF-16 surrogate-pair lookaheads. In a code-point regex engine (ajv's default `u` flag, Python `jsonschema`) they match nothing, so tag characters, the U+E0100 supplement and plane 15-16 private use validate there. The server `TextPolicy` is authoritative; **no other consumer may treat schema validity as TextPolicy validity**, and the redteam fixtures prove nothing for a non-UTF-16 validator. An ajv code-point validator run in the web test suite is a **requirement before the web client consumes these schemas** (section 12).
- **Stored value is plain text, trusted nowhere.** It is **escaped at each sink**: HTML-escaped for any HTML sink (including a Google Calendar `description`), RFC 5545 TEXT escaping plus 75-octet folding for ICS, formula-prefix neutralization (`=`, `+`, `-`, `@`, tab, CR) for CSV, and no markdown in Docs. The Web UI renders text nodes only (C-28). Snippet and notes text must not flow into any calendar description without a separate contract and review. Strings such as `=HYPERLINK(...)` or `<img onerror>` are therefore legal stored text (fixtures `*--redteam-formula-title-as-text`, `*--redteam-html-title-as-text`) and are inert because of escaping, not because they are rejected. A URL the output sanitizer removed from model text cannot be re-added by the student into a field that reaches a sink, because sinks escape rather than link.
- Fixtures: rejected: RLO, zero-width, isolates, tag characters, CRLF, **a single trailing LF in a title, id, date, time, zone, hash, notice version and idempotency key**, NUL, tab, DEL, line separator, C1, 10 combining marks, leading/trailing space, bidi/CR/NUL/too-many-lines in notes, and the verified bypasses: variation selectors (BMP, Mongolian, supplementary), U+034F, Hangul fillers, braille blank, U+FFFC, U+1D173, private use, NBSP and U+3000 as leading, trailing or whole value, stray and astral-block combining marks, ZWNJ/ZWJ at the edges, doubled or next to a space; accepted: Persian with ZWNJ, ZWJ emoji family, VS16 emoji, keycap emoji, Hindi conjunct, supplementary CJK. Lone surrogates cannot be written into a JSON fixture and are covered by `SyllabusPreFreezeTests` through a real JsonSchema.Net evaluation of the shared definitions.

### 2.3 Date and derivation rules (normative; server tests)

`localDate` is limited to the years 2000-2100 and must be a real calendar date (Feb 29 only in leap years). `termStart`/`termEnd` are sent together or not at all (a lone one is `400 validation_failed` with `errors.termStart: ["required"]`, Lead decision 61; JSON `null` counts as not sent) and must satisfy `termEnd >= termStart` and a span of at most 400 days, else `400`. `defaultTimezone` and item `timezone` must be on the closed server allow-list of Area/Location IANA zones. For UTC the only accepted id is `Etc/UTC` (what the web client sends for a browser that reports `UTC`); bare `UTC`, `GMT`, `Etc/GMT` and fixed-offset `Etc/GMT+n` zones are `400` (`not_allowed`). A stated zone abbreviation (for example "ET") is mapped only when consistent with the region of `defaultTimezone`; otherwise the zone is `timezone_assumed` and the item is `please_check`. A nonexistent local time (spring-forward gap) is `dst_ambiguous` and `please_check`. Recurrence requires `from <= until`, `until - from` at most 400 days, at most 20 `exceptions`, and occurrences are generated by code and **capped at 60 when written**, not only at sync. `endDate >= date` for every item. All-day `endDate` on the wire is **inclusive**; a real provider whose end is **exclusive** converts at its boundary (section 15, `calendar.v1` entry criteria).

### 3.1 Extraction status

`status` is one of `queued`, `extracting`, `proposing`, `ready`, `needs_text`, `partial`, `failed`.

- `queued`, `extracting`, `proposing` are in progress: `pollAfterSeconds` is an integer (suggest 2, backing off to 5), `statusReason` is null. All other statuses have `pollAfterSeconds: null`. The UX three steps map to `queued`/`extracting` (got file, finding dates) and `proposing` (getting items ready).
- `ready`: items available, `statusReason: null`.
- `needs_text`: no usable text layer; `statusReason` is `no_text_layer`. The student may paste text (a new syllabus). Entering items by hand needs a `ready` or `partial` syllabus (item create is `409 invalid_state` otherwise, section 5), so a `needs_text` or `failed` syllabus never holds student-authored work and the debris purge (5.3) cannot delete any (R3-13). No OCR in this slice.
- `partial`: some pages or chunks processed; `statusReason` explains (`budget_limited`, `timeout`, `provider_unavailable`, ...) and `unprocessedRanges` and `document.unreadablePages` name the pages. The UI must disclose them; a partial result is never presented as complete.
- `failed`: nothing usable; `statusReason` is one of `unreadable_file`, `password_protected`, `too_long`, `provider_unavailable`, `timeout`, `invalid_output`, `disabled`, `budget_limited`.
- `statusReason` values: `no_text_layer`, `unreadable_file`, `password_protected`, `too_long`, `budget_limited`, `provider_unavailable`, `timeout`, `invalid_output`, `disabled`.
- Cancel is `DELETE /syllabi/{id}` (nothing is kept). There is no `cancelled` status.
- `aiSource: "mock"` forces `demoSource: true` (same visible "Demo source" rule as API_CONTRACTS section 12.2). Only Development/Test may produce `aiSource: "model"`, and only after PO-4 and G2 are cleared; the contract does not authorize it. A configuration flag is not a human gate (R2-21): outside Development/Test the host refuses to start with a model provider whatever the configuration, and enabling it in Development/Test requires a deployment-time control owned by the release process; the gate-register entries (G1, G2, PO-4) are the precondition.

## 4. Item

Fields: `id`, `syllabusId`, `courseId`, `itemKey`, `origin` (`ai` | `student`), `kind`, `title`, `notes`, `when`, `recurrence`, `confidence`, `confidenceReason`, `flags[]`, `snippet`, `edited`, `decision`, `syncState`, `syncedRevision`, `revision`, `etag`, `createdAt`, `updatedAt`.

- **`kind`** is one of `assignment`, `exam`, `reading`, `office_hours`, `policy`, `other`. `policy` is AI-assigned only, informational ("Good to know"), has no date and is never approved or synced. The AI design's finer kinds are mapped by the server: `quiz` -> `exam`, `project_milestone` and `other_deadline` -> `assignment`, `class_meeting` and `no_class` -> `other` (provisional; the finer kind is not on the wire).
- **`when`** (strict): `status` is `resolved`, `needs_date` or `not_applicable`.
  - `written` holds what the document says (`dateText`, `timeText`, `parts{year,month,day,weekday}`), null when nothing was written. This is evidence for display, not the value used.
  - `date`, `endDate`, `time`, `endTime`, `timezone` are the **server-derived** local values. `timezoneSource` is `stated_in_source`, `course_default` or `student`. `derivation` is `explicit_full`, `year_from_term`, `relative_to_anchor` or `student_entered`.
  - `resolved` requires `date`, `timezone`, `derivation`; `unknownReason` is null.
  - `needs_date` (first-class): `date`, `endDate`, `time`, `endTime`, `derivation` are null, `allDay` is false, and `unknownReason` is set: `not_stated`, `tba`, `relative_unresolvable`, `conflicting`, `ambiguous_format`, `table_unreadable`, `date_not_verifiable`. For `conflicting`, `alternatives` lists up to 3 candidate dates; the server never picks one.
  - `not_applicable` is used only by `policy`.
  - Relative dates (`relative_to_anchor`) are resolved only against a term the **student** supplied at creation; a term the AI read from the text is not trusted. Confidence is capped at `probably_right`.
- **`recurrence`** (weekly only): `byDay`, `startTime`, `endTime`, `from`, `until`, `untilSource` (`stated`, `term_end`, `student`), `exceptions[]` (dates). `when.date` is the first occurrence.
- **`confidence`** is a **server-derived enum** `looks_right`, `probably_right`, `please_check`. There is no numeric score on the wire (the schema forbids the field); `confidenceReason` is a short fixed-vocabulary explanation. `looks_right` requires an explicit full date, a verified snippet and no conflict flag. A resolved item with `tentative_language`, `weekday_mismatch`, `table_layout_risk`, `outside_term`, `injection_suspect`, `supersession_cue` or `low_text_quality` is `please_check` (schema-enforced for the last three). Confidence is **re-derived on every edit**: a student-entered date is never `looks_right` (schema-enforced) and is not batch-eligible. **Editing an AI item (R2-07):** any edit of `date`, `endDate`, `time`, `endTime`, `allDay`, `timezone` or `recurrence` on an item whose `origin` is `ai` re-derives it as `derivation: "student_entered"`, `timezoneSource: "student"`, `edited: true`, and drops `confidence` to `please_check` with a fixed `confidenceReason` (schema-enforced for `origin: "ai"`), because its snippet no longer supports the value. A `kind`, `title` or `notes` edit also sets `edited: true` and the item is no longer batch-eligible (batch approve requires `edited: false`), but keeps its confidence. A student-origin item may be `probably_right`. `looks_right` is a statement that the value was derived from the text, **not** that the text is true; its label must not read as "verified".
- **`flags`** vocabulary: `year_inferred`, `relative_date`, `timezone_assumed`, `time_missing`, `conflicting_sources`, `tentative_language`, `table_layout_risk`, `section_ambiguous`, `range_end_inferred`, `weekday_mismatch`, `date_not_verifiable`, `until_from_term`, `low_text_quality`, `duplicate_candidate`, `outside_term`, `dst_ambiguous`, `injection_suspect`, `supersession_cue`. Server flags win; the model cannot remove them.
- **`snippet`**: `{text, start, end, page, precision, context}`; `precision` is `exact` (offsets into the stored canonical text; `end - start` equals the text length, tested) or `line` (redaction prevented an exact match; offsets cover the line range). Null only for `origin: "student"`; required for `origin: "ai"`. **Offsets are UTF-16 code unit offsets** into the canonical text (the .NET `string` index), never code point or byte offsets, and **all slicing is done in .NET, never in SQL** (PostgreSQL `substr` counts code points, so an emoji before the snippet would shift every later offset; fixture `syllabus-item--snippet-emoji-before` and a contract test pin this). `context` is the server-sliced **context window** (the full line or paragraph around the snippet, at most 1,500 code points, with `start <= snippet.start` and `snippet.end <= end`); it is how the student judges a verbatim snippet now that the original is gone. **`snippet.text` is nullable (R2-04):** after the retention purge (section 5.3) `snippet.text`, `snippet.context`, `snippet.start` and `snippet.end` are all `null` (schema-enforced together; none survives alone, since offsets are meaningless without the text) while `page` and `precision` remain. `snippet.text` is never null while the canonical text exists, and never an empty string. Clients must render a `null` snippet as "The original wording was removed on schedule", not as an error. `snippet.context` is likewise `null` only after the purge. There is no "view in document" and none will be added (section 13 row 27).
- **`decision`** is `undecided`, `approved`, `skipped`. **`syncState`** is `not_synced`, `synced`, `changed_since_sync`, `sync_failed`.
- Cross-field rules enforced by the schema (and re-checked by the server): a `needs_date` or `not_applicable` item can never be `approved`; any `syncState` other than `not_synced` requires `decision: "approved"`; `synced` and `changed_since_sync` require an integer `syncedRevision` (1 to 2147483647), `not_synced` requires `null`, and **`sync_failed` allows `null` (R2-11)**: `syncedRevision` is `null` when the first sync of the item failed (it was never written) and the last successfully written revision when a re-sync of an already-synced item failed. The failure reason lives only in the sync result, never on the item; `kind: "policy"` if and only if `when.status: "not_applicable"`; student items have no snippet and never `policy`; `allDay` forbids times; `endTime` requires `time`.
- **`edited`** is true once the student changed any value. The original AI proposal remains in provenance (invariant 5) and is not on the wire in v1 ("Reset to what we found" is deferred, section 15).
- Fine-grained rule: the item **title and kind are our wording** (a paraphrase), the snippet is the evidence. The review row shows title and snippet together; a deterministic server check flags a `kind` whose keywords contradict the snippet as `please_check` (flag only).
- Default length: a timed item with no `endTime` becomes a 60 minute event (decision 7); the event carries `endDerived: true`. A timed event crossing midnight is allowed.

### 4.1 `itemKey` (idempotency basis)

`itemKey = "ik_" + first 32 characters of base64url(SHA-256(UTF-8("tether.syllabus.item.v1\n" + syllabusId + "\n" + itemId)))`, no padding. Derived from (syllabusId, itemId) only, so it never changes on edit, undo or re-approval, and a future Google provider reuses it as its idempotency key (`extendedProperties` or equivalent). Contract tests recompute it for every fixture. Recurring occurrences use `itemKey + ":" + occurrenceDate`. `itemKey` is an idempotency basis only; it is never an identifier any endpoint accepts and never an authorization token.

Notes
- **Duplicate content.** Identical content hash in the same course returns `409 duplicate_syllabus` with `existingSyllabusId` in the problem body, unless the request sets `allowDuplicate: true`. The lookup is `(userId, courseId, contentSha256)`; a duplicate check never reveals another user's upload. `allowDuplicate: true` counts as a new extraction against the daily quota and the AI budget.
- **Quotas.** One extraction in flight per user (`409 extraction_in_progress`, enforced by a unique partial index on `(user_id)` for statuses `queued`, `extracting`, `proposing`); at most 5 syllabi per course and 50 active per user (`409 syllabus_limit_reached`). Syllabus creation is limited to 10 per day per user, counted at creation and **never refunded** on cancel or failure. The count is a **dedicated durable per-user creation counter** (user id, UTC day, integer; content-free), not derived from AI usage rows, so it works and is testable in mock mode where no AI cost row exists (R2-19).
- **Term and zone.** `termStart`/`termEnd` are optional and student-supplied at creation (rules in section 2.3); `defaultTimezone` is required (browser or profile value, validated against a server allow-list). Changing them later is deferred (delete and re-add).
- **Notice and attestation.** `noticeVersion` and `attestation` (`accepted: true`, `acceptedAt`) are required on create and stored on the syllabus as `notice` (`version`, `attested`, `attestedAt`) with a content-free audit row (user, syllabus id, version, time, and at most an HMAC-SHA-256 of the content hash with a server key, never a plain content hash; no text). **`notice.attestedAt` is the server's receipt time (R3-11).** The client `attestation.acceptedAt` is advisory only: it is validated for shape, may be kept separately as "claimed" within a skew bound (for example 24 hours), and is never used as the consent record, so a client cannot backdate it. The notice and attestation wording is a **DRAFT placeholder owned by the Product Owner and counsel (P2-D5)**; the UI must not imply Tether verified that the student may upload the document. The only document-type sanity check is a **warning** ("this does not look like a syllabus"); nothing classifies the student or the document into sensitive categories, and disability or health information is never logged or inferred.
- **Pagination of items** is by `(effective date, id)`; items needing a date sort last.
- **Clarifications (commit 033b79d, no wire change).** (1) A paste body that is not fully read within the read deadline (default 30 s, `Syllabus:PasteReadSeconds`, 1-120) ends as `400 validation_failed`, the same answer a slow upload gets, and releases the create slot and the bytes-in-flight reservation. (2) `counts.droppedInvalid` includes dropped unclaimed dates as well as dropped items (capped at the wire maximum of 1000). (3) An item dropped for an invalid model-written field whose verbatim snippet is still valid is kept as an unclaimed date from the server-sliced source snippet (never model text); it is **both** counted in `droppedInvalid` and listed in `/unclaimed-dates`, so UI copy must not say the date "could not be read".
- **No malware scan.** No uploaded file is ever served, rendered or downloaded back, so v1 needs no AV scan; the risk is parser exploitation (section 5.1). If original download is ever added it needs AV and its own review (section 15).

### 5.1 Upload and extraction hardening (normative; the extractor may not merge without the hostile fixtures in section 12)

1. **Sniff, do not trust.** The type is decided by magic bytes (PDF `%PDF-`, DOCX = ZIP with `[Content_Types].xml` and `word/document.xml`, plain text). An extension, `Content-Type` and signature that disagree are `415 unsupported_type`. The client filename is discarded at parse time: never stored, logged, echoed in `detail`, or used for a path.
2. **Streaming caps, request shape.** The 10 MB limit is enforced **while reading** (Kestrel `MaxRequestBodySize` per endpoint, `MinRequestBodyDataRate`, request timeout), never by trusting `Content-Length`. Exactly one `file` part and one `metadata` part (at most 4 KB); anything else is `400`. The request is rejected before buffering. A global cap bounds concurrent uploads and total bytes in flight (item 9). **One concurrent streaming upload per user (R3-05):** a second concurrent create by the same user is refused before any byte is read (`429 rate_limited`; step 6). Each accepted upload **reserves the full 10 MB cap** against the bytes-in-flight budget (`Content-Length` is never trusted), released on completion, error or timeout. A minimum body data rate and a short overall read timeout (for example 60 s for 10 MB) end slow uploads. A full volume is the same `429` (not `503`).
3. **ZIP/DOCX.** Caps on entry count, per-entry and total uncompressed bytes, expansion ratio (zip bomb), path depth; any `..` or absolute path rejects the file. Macro or VBA parts (`vbaProject.bin`, macro-enabled content types), OLE and embedded packages reject the file. Relationships with `TargetMode="External"` are ignored and never fetched.
4. **XML (DOCX parts).** DTDs prohibited (`DtdProcessing.Prohibit`), `XmlResolver = null`, entity-expansion and character limits (`MaxCharactersInDocument`); a DOCTYPE or external entity (XXE, billion laughs) rejects the file. Verify on the chosen parser.
5. **PDF.** Never rendered. `/OpenAction`, `/Launch`, `/URI`, `/JavaScript` and `/EmbeddedFile` are ignored (never followed or extracted). Page count is read from the page tree and compared with 60 **before** text extraction; decompression is bounded. Encrypted becomes `failed` with `password_protected`. Hidden text (render mode 3, background-colored, off-page, under about 1 pt) is **dropped before the AI sees it** and counted in `document.hiddenContentRemoved`.
6. **Plain text and paste.** NUL rejects; UTF-8 or UTF-16 with BOM only. Pasted text is treated **exactly like a file**: same TextPolicy canonicalization (section 2.2), limits, retention (5.3), deletion and hash.
7. **Output cap.** Extraction stops at 50,000 characters and the page cap **during** extraction, not after.
8. **Trusted orchestrator versus untrusted parser (R2-12).** Two components with different trust. The **orchestrator** (the Syllabus module's job worker) owns the database connection, the user context and the job lease; it never parses. The **parser worker** is a separate process or container that is treated as compromisable: **no network, no database credentials (no connection string, no DB socket or driver in its image), no secrets or environment of the API**, a read-only filesystem except its scratch directory, non-root, and bounded CPU, memory and wall time (60 s). The orchestrator hands the parser a file path on the shared ephemeral volume (or stdin) and receives only canonical text plus counts over stdout/IPC; it then **re-validates the output** (size and page caps, TextPolicy canonicalization, counts) as untrusted. A parser crash, timeout or malformed output is `failed` with `unreadable_file` or `timeout`; parser exceptions are mapped to codes before logging and never logged or returned as text. An architecture test requires that the parser assembly references neither the persistence, HTTP client nor logging-sink packages. **Process roles (R3-03):** (a) the **web-facing API** authenticates, checks Origin, applies limits and sniffs the first bytes; it never writes upload bytes to disk and the ephemeral volume is **never mounted into the API container**; it relays the multipart stream over an internal authenticated channel to (b) the **ingest worker**, a separate trusted worker process/container (this is the "orchestrator"; it is not the request handler) which mounts the volume, writes the file (hashing in the same pass), owns the database connection and job lease, and launches (c) the **parser sandbox**. **One fresh sandbox per job (R3-03):** a new container or process with namespaces, seccomp, no network and no DB credentials, given **exactly one input file** (a single-file read-only bind or an inherited file descriptor / stdin), destroyed after the job; there is no long-lived or shared parser, so a compromised parser can read neither another user's upload nor any state from a previous job. **Output channel (R3-04):** document text never travels on the parser's stdout or stderr. The structured result (canonical text plus counts) is returned through a result file on the job's private scratch directory or a pipe/socket owned by the ingest worker; the sandbox's log driver is set to `none` (or stdout/stderr discarded) and only the exit code is captured, because container log drivers would otherwise write the canonical text of every syllabus into host logs. The ingest worker reads the result with a bound (4x the character cap) and kills the sandbox on overflow. A log-driver canary test (a canary in file content, through parser crash and timeout, must not appear in any host, container or orchestrator log sink) is required (section 12).
9. **Transient bytes (R2-12, R2-13, decision changed 2026-10-28).** Upload bytes are **never written to Postgres**: not a table of any kind, not a job payload row, not a `bytea` parameter. They are streamed to a **tmpfs / ephemeral volume** (**memory-backed tmpfs is required (R3-06)**: `medium: Memory` or `--tmpfs` with a `size=` limit; never a persistent, node-local or snapshotted disk, never object storage, never a versioned bucket) that is mounted **only** into the ingest worker and, per job, the single input file into that job's sandbox (item 8); that volume is excluded from backups and snapshots by construction. They are deleted when the parser finishes (success, failure, cancel), on `DELETE`, and by a sweeper with a hard ceiling of **within 1 hour**, tested with a killed worker. A **global cap on bytes in flight** (for example 10 uploads x 10 MB, configurable) bounds the volume; at the cap a new upload gets `429 rate_limited` at step 6, before any byte is read. Because the bytes never enter the database, database statement and parameter logging, `auto_explain`, `pg_dump`, WAL and replication do not touch them (nothing to turn off), and the earlier database-table design and its residual risk list are withdrawn. Remaining risk, accepted with controls: bytes on a node-local tmpfs can be swapped (disable swap or use an encrypted swap), and appear in a core dump (disable core dumps for the worker); the volume is never mounted into the API container and the parser has no route to remove its own output other than the orchestrator. This is the only retention statement for bytes: the earlier 24 h figure in P AC5 is superseded and the conflict is resolved to 1 hour. Because the original is not kept, retrying a failed extraction needs a new upload; after `ready` the canonical text and items persist (5.3). `docs/data/schema-syllabus-p2.md` must drop any table or column that holds upload bytes (database-architect); security-engineer to re-confirm the revised design.
10. **Extraction cache.** None across users. Content hash, any extraction cache and idempotency basis are scoped by `(userId)`; there is **no cross-user** reuse of extraction results, canonical text or items. A shared cache of model output needs its own review and is out of scope for v1.

### 5.2 Delete (exhaustive, one transaction)

`DELETE /syllabi/{id}` hard-deletes in one transaction: items, revisions, approvals, unclaimed dates, canonical text and lines, snippets and context, extraction jobs and their ephemeral bytes, idempotency records (a create key is reduced to a content-free tombstone until its 24 hour expiry, section 2.1), the dedupe hash row, sync runs, and **the mock calendar events (always)**. The `keep` option is dropped from v1: there are no orphaned events. A running job is cancelled; every job writer re-checks the syllabus still exists, so a late result cannot recreate data (extends C-21, with a late-writer test). Course archive/delete and account delete cascade the same way and are tested. Only content-free rows survive (AI usage ledger totals with scope id and cost; audit rows with ids, counts and times; the create-key tombstone; the daily creation counter), and they are listed in the data model. Backups roll off on the platform's schedule (target at most 30 days including backups; a restore can resurrect a deleted syllabus until deletions are re-applied, see `docs/data/schema-syllabus-p2.md`). Copies already sent to a model vendor (when real) or exported files are not deleted by this call, and the delete confirmation must say so. Test: delete, then query every table, cache, queue and temp path for the syllabus id and its content hash, **allowing only the named survivors (R3-12)**: AI usage ledger totals, audit rows with ids, counts and times (which carry no plain content hash and, if they keep one, only its HMAC), the create-key tombstone (no syllabus id, no content hash) and the daily creation counter.

### 5.3 Retention (provisional, PO-owned; open D4/D11 follow-ups)

All of this is a **Lead decision, provisional where PO-owned**; it is a default to build against, not an approval.

- **What is purged.** The canonical extracted text is the stored source record (invariant 5). It is purged when the syllabus is deleted and otherwise at `retention.canonicalTextPurgeAt`. The retention purge removes the canonical text, **every `snippet.context` and every `snippet.text`** (and the snippet offsets), because the union of 200 short snippets can approximate most of a document and can contain instructor emails and phones. Items **survive** the purge and keep `kind`, `title`, dates, `decision` and sync state; the audit trail and `written.dateText` stay. The notice must say that the text of the document and its excerpts are kept until deleted or purged, and that titles and dates stay.
- **The clock.** `canonicalTextPurgeAt = min(lastStudentWrite + 180 days, createdAt + 365 days)`. **Last activity means student writes only**: item edit, decision (approve, skip, undo), calendar sync or remove, and adding an item. It is **never** extended by reads, polls (`GET /syllabi/{id}`), list or export calls, or job progress. The **absolute maximum is 365 days from creation**, whatever the activity. A background purge job runs the purge and is tested with time shifting (items, snippets and context included).
- **Debris purge (7 days).** Failed, `needs_text` or abandoned syllabi (an upload or extraction job that never produced a usable result, including a stuck `queued` / `extracting` / `proposing` job past its lease) and their job rows are removed 7 days after creation or last job state change, with the same content-free survivors as a delete. This is the data design's stated behaviour, recorded here so the contract, notice and UX agree; it shortens retention and never lengthens it.
- Pasted text is treated exactly like a file. Whether `snippet.text` and items should also be shortened or kept longer is an open PO question (D4/D11, with PO-5 and counsel under P2-24).

## 6. Commands and rules

### 6.1 Decisions (approve, skip, undo)

- `decision: "approved"` requires `when.status: "resolved"`; otherwise `409 item_needs_date` (or `409 item_not_syncable` for `policy`). Enforced on the server **inside the locked decision transaction** (section 2.1), not only in the UI or on a value read earlier. Approving never writes to any calendar.
- Approving a `please_check` item needs `acknowledgeCheck: true`, else `409 acknowledgement_required`. `acknowledgeCheck` is a client-asserted flag that proves only that the client sent it.
- Choosing one of a `conflicting` item's `alternatives` is only done by PATCH of `date`; it is never an approve.
- Approval is recorded in the content-free audit log (user id, item id, revision, timestamp) and applies to the item `revision` that `If-Match` named.
- Undo (`undecided`) and skip (`skipped`) never expire and never time out.
- Setting an item that is `synced`, `changed_since_sync` or `sync_failed` to `undecided` or `skipped` **also removes its mock events in the same transaction** and returns `syncState: "not_synced"`. If the removal fails, the whole command fails with `503 provider_unavailable` and nothing changes. The calendar therefore never holds an item the student has withdrawn. (Mock only: a real provider needs a `pending_removal` state, section 15.)
- **Batch** (`POST /syllabi/{id}/decisions`): `itemEtags` is a JSON object keyed by item id (1 to 100 entries) with the etag the student saw, no "all" form. Because ids are object keys, **duplicate ids are not representable**, and a duplicate member name is `400` (section 2.1), so one id cannot be approved and skipped in one call. Ids that are not in the path syllabus and owner give the same per-item `not_found` as nonexistent ids. **Each item is its own transaction**; the response lists every outcome, and a mid-batch failure never leaves an event for a withdrawn item. `approve` is accepted only for `resolved` `looks_right` items with `edited: false` **and a non-null `snippet.text` (R3-01: after the retention purge there is nothing for the student to read, so `retention.canonicalTextPurged: true` forces `batchApproveAllowed: false`, schema-enforced; those items need individual, acknowledged approval and the UI shows "the original wording was removed" beside the date)** **of a document whose `batchApproveAllowed` is true**; otherwise the item is `rejected` with `batch_not_eligible` (or `item_needs_date`). A stale etag is `rejected` with `precondition_failed`. The response is 200 with per-item results and counts and never claims success when any item was rejected. `skip` and `undecide` follow the same removal rule as above. Per-user (not only per-syllabus) rate limits apply to batch calls (section 11).
- **Hostile-but-verbatim documents.** A document with `injectionSuspect: true`, `hiddenContentRemoved > 0` (`hiddenContentDropped`) or any `low_text_quality` has `batchApproveAllowed: false` (schema-enforced; `hiddenContentRemoved >= 1` forces `hiddenContentDropped: true` and `batchApproveAllowed: false`, and stripped tag characters, bidi controls and other format characters count toward `hiddenContentRemoved`, section 2.2), and every item from it is `please_check`: batch approve returns `batch_not_eligible` for the whole syllabus and each item needs an individual, acknowledged approve. See section 8.

### 6.2 Edit

- Allowed on any non-`policy` item: `kind` (not to `policy`), `title`, `notes`, `date`, `endDate`, `time`, `endTime`, `allDay`, `timezone`. Merge-patch rules: absent = unchanged; `null` is legal only on fields the schema marks nullable (`notes`, `endDate`, `time`, `endTime`); `title: null`, `kind: null` and `date: null` are `400` (a date cannot be cleared). Setting `date` on a `needs_date` item makes it `resolved` with `derivation: "student_entered"`, `timezoneSource: "student"`, `edited: true`, and it stays `undecided`. `timezone` alone on a `needs_date` item does not change `when.status`. **Editing the date, time, end or zone of a resolved AI item (R2-07)** re-derives it as `student_entered` and drops confidence to `please_check` (section 4). Edits to a `policy` item are `409 item_not_syncable`.
- Student edits are exempt from source-derivability checks (the student is the authority) but still need real calendar dates in the 2000-2100 window and `endDate >= date`. Text edits pass TextPolicy (section 2.2).
- Editing an **approved, not yet synced** item returns it to `undecided` (approval belongs to the revision that was approved). Editing a **synced** item keeps it `approved`, sets `syncState: "changed_since_sync"` and does **not** touch the calendar; the next explicit `calendar-sync` shows and applies the change (`outcome: "updated"`).
- Content edits bump `revision`; every mutation changes the etag (section 2.1).

### 6.3 Calendar sync (mock)

- Request names `itemRevisions` (item id to the revision the student reviewed) and carries `confirm: {provider: "mock", acknowledgedDemo: true}`. Nothing is written without it. Only items that are `approved`, `resolved` and at the named revision are eligible; every other id yields `outcome: "not_eligible"` (or `failed` with `precondition_failed` when the revision moved) with `errorCode` (`item_not_approved`, `item_needs_date`, `item_not_syncable`, `precondition_failed`, `not_found`) and **zero writes**. The check and the write happen in one transaction that locks the item rows (`SELECT ... FOR UPDATE` or a concurrency token), so a concurrent edit, skip or withdraw cannot leave an event for a withdrawn item.
- Outcomes per item: `created`, `updated` (an existing event for the same `itemKey` changed), `unchanged`, `failed`, `not_eligible`. Overall `status`: `all_succeeded`, `partial`, `failed`, `nothing_to_do`. HTTP is 200 for every outcome; the result never reports full success when any item failed. A failed item stays `approved` with `syncState: "sync_failed"`; a retry does not duplicate the others. For an item that was **never synced** the item resource carries `syncedRevision: null` in `sync_failed` (R2-11, section 4); for an item that had synced before it keeps the last written revision. The reason is only in the sync result.
- **Caps.** At most 1,000 events per syllabus and a per-user ceiling (section 10) are enforced at sync; an item whose occurrences would exceed them fails with `event_limit_reached` and writes nothing for that item. Sync accepts up to 100 items per call and writes at most 500 events per call; the rest are `failed` with `event_limit_reached` and can be retried in another call. The export caps equal these write caps. **Processing order (R2-15):** items are processed in ascending effective date (`sortDate`, items without a date last) then id, never in JSON member order, so "the rest fail with `event_limit_reached`" is deterministic. The per-user event ceiling is checked under a **per-user advisory lock** (in addition to the syllabus row locks), so two syllabi syncing at once cannot both pass it.
- **Idempotent.** The mock event for an item is keyed by `itemKey` (and the occurrence date for recurrences). Running sync any number of times, or replaying the same `Idempotency-Key`, yields one event per item (`unchanged` on repeat). A replay returns the original body with `Idempotency-Replayed: true`; its states can be stale by design (section 2.1).
- `calendar-sync/remove` deletes mock events and returns items to `approved` / `not_synced` (the decision is kept). Remove then re-add produces exactly one event. Outcomes: `removed`, `not_present`, `failed`. Ids outside the path syllabus are per-item `not_found`.
- Events are stored with provider, event id, item id, `syncedRevision` and time, in the database only (C-22). Fault injection (timeout, 500, rate limit) is allowed only in Development/Test and fails startup elsewhere (same rule as `Speech:Replay:Faults`).

## 7. Real-time and background work

No hub. A background job (existing Postgres jobs pattern) runs extraction; the client polls `GET /syllabi/{id}`. The job has a **lease with heartbeat and a reaper** (reuse the reservation-reaper pattern), so a crashed or stuck worker releases the user's single in-flight slot; a unique partial index on `(user_id)` for `queued`/`extracting`/`proposing` prevents two concurrent creates from starting two jobs. The daily quota counts at creation and is never refunded on cancel or failure. A global cap on concurrent extractions and on queue depth answers `429 rate_limited` (or `503`) when full. Deleting a syllabus or its course cancels the job, and every writer re-checks the syllabus still exists so a late job cannot recreate data (extends C-21). Course archive and purge cascade with DB-level `ON DELETE CASCADE` (database-architect to confirm the allow-list entry).

## 8. Privacy, security and logging requirements (normative for implementation)

- The AI sees only canonical text (as untrusted data) plus validated server context (term dates, IANA zone). Never tokens, the student's calendar, ids, names, filenames or other documents; no tools. The Calendar provider never receives AI output without student approval.
- **Hostile-but-verbatim content.** Prompt-injection text in a document is inert (A section 8), but `snippet.text` of a hostile document may still be a false-yet-verbatim date ("Exam 1: Oct 19 (moved from Oct 12)", "the final is NOT on Dec 9"). Trust is not the mitigation. Required, in order: (a) `injectionSuspect`, `hiddenContentDropped` or `low_text_quality` caps every item at `please_check` and sets `batchApproveAllowed: false`; (b) **hidden text is dropped before the AI sees it** (not merely counted); (c) the **server-sliced context window** (`snippet.context`) lets the student read the surrounding line; there is no "view in document"; (d) a deterministic **supersession cue** list sets the `supersession_cue` flag and forces `please_check` (R2-08). **Scope:** matching runs over the snippet **and** its context window (the full line or paragraph), on a matching-only copy of the text normalised with Unicode NFC then NFKC and case-folded (the stored text stays NFC); English only in this slice. **Cues** (versioned data, not code): canceled, cancelled, cancellation, postponed, rescheduled, reschedule, moved, delayed, pushed back, changed, change of, updated, revised, extended, replaced, instead, formerly, previously, no longer, is not, will not be, won't be, not held, not on, unless, except, tbd, tba, to be announced, subject to change. There is **no bare "not"** (too common: it would flag nearly every item and train students to click through). The list is calibrated on synthetic syllabi for false positives before release, is a heuristic and not a guarantee, and a cue it misses is the accepted residual below; (e) mandatory individual approval for anything not `looks_right`. **Accepted residual (R2-09):** a hostile or simply wrong document with a plain, visible, cue-free false date remains `looks_right` and batch-approvable, because the server cannot know whether the student read the snippet. UI contract (adhd-ux, frontend): batch approve shows the snippet and context for each selected item, and no label ever reads "verified". Red-team fixtures (misleading verbatim date, hidden text, supersession) are required before the AI seam merges (section 12).
- **Budgets (when a real model exists).** The syllabus workflow has a **separate budget pool** (scope `SyllabusExtract`; a `pool` dimension on the usage ledger and counters, so per-user daily caps, per-job caps and the floor are **per pool**, and a large syllabus can never use up a student's daily allowance for lecture AI), not shared with lecture features, with a ceiling for the pool and a protected floor for live-lecture workflows so syllabus load cannot starve them; a per-user daily spend cap (not only a count), a per-job cap, a global kill switch and spend alert, and the whole-job pre-flight check from A section 9. `allowDuplicate` counts as a new extraction. Sign-up throttling is an input. Exhaustion surfaces as `partial`/`failed` with `budget_limited`, never silently. Real Claude stays off until PO-4 and G2.
- **Logging.** Logs carry id hashes, sizes, counts, versions and validation codes. Never document text, snippets, context, titles (including the syllabus `title` supplied at create), notes, prompts, completions, **filenames** (multipart `Content-Disposition`, form-file models) or **parser exception text** (PDF/XML libraries embed object text, entity names and paths in messages; exceptions are mapped to codes before logging). `ProblemDetails.errors` never echoes a rejected value. EF sensitive-data logging stays off; job payloads, the AI usage ledger and OpenTelemetry attributes carry no item text. The log canary (C-23) applies: a canary placed in file content (a PDF stream, a DOCX table cell, a paste, a filename), in a syllabus title and in an item title/notes must not appear in any log, trace or metric sink at Trace level with EF sensitive logging on, including under fault injection (parser crash, XXE attempt, invalid AI output, DB failure). This canary test is a required check before the Syllabus module merges.
- **Export.** Owner-scoped, generated on demand, never a public or signed URL; JSON only; headers `Cache-Control: no-store`, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`; rate-limited (6 per minute per user). Export holds items, snippets and events (snippets can carry instructor emails and phones that the AI never saw); it holds no original file because none is retained. Future ICS/CSV exports inherit TextPolicy escaping and need their own review.
  - **Cross-site requests (additive clarification, 2026-10-31, SB-07).** Export writes an audit row and spends the export budget, so it is not treated as a safe GET. The method, path, response and success status are unchanged. The server answers `403 csrf_failed` (evaluation step 2, before any id or ownership check) when the request carries a `Sec-Fetch-Site` header whose value is anything other than exactly `same-origin` or `none`, carries more than one such header, or carries an `Origin` header that is not an allow-listed origin. A request with no Fetch Metadata (a non-browser client or an older browser) is still served. Clients must call export with a same-origin `fetch` (the web client does: same-origin proxy, ADR-006), never through a link or redirect from another site. `403 csrf_failed` is an existing code; no schema changes.
- **Audit.** A content-free audit event (user, ids, counts, time; SEC-028) is written for create, approve, sync, remove, delete and export.
- **Dropped content.** Hidden content (DOCX `vanish` runs, comments, metadata, PDF hidden text) is dropped and counted in `document.hiddenContentRemoved`.

## 11. Rate limits (proposals)

The global 120/min read limit applies. **Syllabus routes have their own buckets, separate from the 30/min live-lecture write bucket (R2-14):** a **syllabus write bucket** (proposal 20/min per user, covering upload, item create, patch, decision, batch, sync, remove and delete) and a syllabus read bucket (proposal 120/min per user, polls included), so a syllabus flood or a buggy client can never throttle a student mid-lecture or block "Quick recap".
